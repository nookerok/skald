# Living World — Architecture

Сводный документ всех решений, согласованных в ходе обсуждения. Версия: после уточнений по Consequences / Situations / Observations / Authority Hierarchy / детерминированности / Projection Purity.

## Инварианты конституции (не подлежат нарушению)

Краткая справка — подробности и обоснование каждого пункта в соответствующих разделах ниже.

- Event Log — единственный источник истины (§2.1) и **append-only**: записанные события никогда не изменяются и не удаляются.
- Projection Purity: World Projection полностью вычисляется из Event Log и не хранит ничего, чего там нет (§9.6).
- Rules — чистые и детерминированные функции `(Event, ReadonlyWorld) → Event[]` (§2.2, §9.1).
- LLM/Narrative никогда не авторитетны и не принимают решений за игру или за персонажа игрока (§6, §5.13, §5.8).
- Runtime-генерация правил запрещена в v1; прогресс = активация уже существующих правил (§5.2).
- Запрет `NPC.decide()` распространяется и на персонажа игрока в его отсутствие (§5.8).
- Player Command не является Event, никогда не пишется в Event Log и никогда не поступает в RuleEngine/Rule напрямую; переход Command → Event происходит только через Command Handler (§4, §9.9). В Log попадают только Domain Events — свершившиеся факты мира.
- Execution Model: во время обработки одного Event все Rules читают один и тот же неизменный snapshot Projection; canonical Projection обновляется атомарно только после успешного завершения обработки всего top-level Command (§12).

Всё, что не входит в этот список, — предмет обсуждения и может уточняться. Список выше — нет, без пересмотра всей конституции.

---

## 1. Цель проекта

Построить симуляцию живого мира, а не готовую RPG-систему.

- Игрок не изучает заранее прописанную систему магии/классов/навыков.
- Игрок исследует мир, а мир исследует игрока.
- Все игровые механики — следствие законов мира, а не заранее прописанных RPG-систем.

---

## 2. Базовые принципы (неизменны с v1.0)

### 2.1 Events — единственный источник истины

Канонического состояния мира нигде не хранится, кроме журнала событий.

```
Events → World Projection → Current World State
```

Мир в любой момент можно восстановить из журнала событий с нуля.

**Append-only.** Event Log является append-only: уже записанные события никогда не изменяются и не удаляются. Любое новое знание о мире (включая исправления, отмены, коррекции) выражается новым событием, а не редактированием старого.

### 2.2 Rules — единственная игровая логика

Любая механика существует только как Rule.

```
Rule: (Event, ReadonlyWorld) → Event[]
```

Правило:
- ничего не мутирует;
- не вызывает другие правила напрямую;
- не знает про UI;
- не знает про LLM;
- **эмитит только новые события.** Входящий Event и любые уже существующие Events immutable и не могут быть возвращены повторно, обёрнуты или изменены в `Event[]` — только вновь созданные факты.

### 2.3 Infrastructure ≠ Gameplay

Разрешены только инфраструктурные компоненты:
- EventBus
- RuleEngine
- WorldProjector
- CLI
- Narrative Adapter
- Command Handler (см. §4, §9.9 — структурная валидация PlayerCommand, без доступа к World, не Rule)

Вся игровая логика живёт исключительно внутри Rules. Ничего игрового не должно появляться в инфраструктурном слое, включая Command Handler — он не принимает игровых решений (не проверяет стены, время, принципы), только структурную корректность самой команды (известный ли тип действия, есть ли обязательные поля).

### 2.4 Intent вместо заклинаний/способностей

Игрок не выбирает способность из списка. Игрок описывает намерение.

Пример: `расплавить петли`, а не `Fireball`.

### 2.5 Прогресс — открытие законов мира, а не уровни

Нет: XP, уровней, классов, дерева навыков.

Есть: открытые Principles (например Heat Transfer, Weak Point, Living Flame, Echo Resonance). Каждый открытый принцип активирует уже существующее правило (см. §5.2).

### 2.6 Мир учится в ответ на поведение игрока

Мир накапливает наблюдения о действиях игрока и это со временем порождает последствия (см. §5.3, Observations). **Важно:** в v1 это не означает генерацию новых правил — см. §5.2.

### 2.7 Философия мира (фундаментальный принцип)

Эти пункты задают тон всей архитектуре и защищают от отката к привычной RPG:

- Мир существует независимо от игрока. Его процессы (Situations, §5.4) продолжаются, пока игрок офлайн, и не приостанавливаются в его отсутствие.
- Игрок исследует законы мира, а не набор игровых механик и не карту.
- Любое изменение в мире должно объясняться внутренними законами мира (Rule), а не сценарием или волей Narrative-слоя.
- LLM никогда не создаёт факты — он только описывает уже случившиеся события.
- Любая сложная система (экономика, война, слухи) возникает из множества простых правил, а не проектируется как отдельный "движок".
- Новые возможности игрок открывает через понимание мира (Principle), а не через получение уровней или очков.

## 4. Архитектура пакетов (v1 / MVP-0)

```
packages/
  event-bus/
  rule-engine/
  world/
  intent-parser/
  cli/
```

Больше пакетов на этом этапе создавать нельзя. Расширение функциональности (Consequences, Situations, Observations, Biography) реализуется **внутри существующих пакетов** (в основном `world/` и `rule-engine/`), а не через новые top-level пакеты.

**Роль Simulation-слоя:** в ранних набросках фигурировала цепочка `Intent → Parser → Validator → Simulation → Events`. Отдельного пакета `simulation/` не создаётся — эту роль выполняют `rule-engine/` и Command Handler вместе: Command Handler (см. §9.9) переводит `PlayerCommand` в первый Domain Event (`<Action>Requested`), а дальнейшая валидация (в т.ч. проверка временного бюджета, см. §5.12) — это обычные Rules, реагирующие на этот Domain Event и либо эмитящие `ActionRejected`/`MovementBlocked`, либо продолжающие обработку до Domain Event, отражающего успех. RuleEngine при этом никогда не видит `PlayerCommand` напрямую — только Domain Events.

### Event Flow

**Command ≠ Event, и RuleEngine никогда не видит Command.** Domain Event описывает факт, который уже произошёл в мире, а не попытку его изменить. Поэтому команда игрока обрабатывается в два строго разделённых шага:

```
Player → PlayerCommand (не хранится)
  → Command Handler (infra, НЕ Rule, без доступа к World —
      только структурная валидация: известен ли тип команды,
      есть ли обязательные поля)
  → либо CommandRejected (Domain Event, структурная ошибка)
  → либо первый Domain Event "<Action>Requested" (например MoveRequested)
       ↓ (записывается в Event Log)
  → RuleEngine (обрабатывает только Events, Command никогда не видит)
  → Rules по фазам (Validation → Physics → Consequence → Notification)
  → новые Domain Events (ActionRejected / MovementBlocked / MovementSucceeded / ...)
  → World Projection → Current State → Narrative
```

`PlayerCommand` (например `MoveCommand`) никогда не попадает в Event Log — это транспортная/интерфейсная сущность. Все дальнейшие события — Domain Events, отражающие факты мира: свершившееся действие (`MovementSucceeded`) или отклонённую попытку (`MovementBlocked`, `ActionRejected`) — отклонение тоже факт (мир узнал, что попытка не удалась), и это может повлиять на Observations/Consequences (см. §9.9).

RuleEngine никогда не вызывает Rule напрямую — только через очередь событий:

```
queue → pop() → run rules → append new Domain Events → repeat
```

### World

World — ReadOnly для Rules. Единственный разрешённый результат работы правила — `Event[]`. Изменение состояния происходит исключительно внутри Projector.

### Testing

Каждое правило имеет собственный unit-тест по шаблону:

```
Given: Event + Readonly World
When: Rule
Then: Expected Events
```

Интеграционные тесты запрещены до появления минимум пяти рабочих правил.

### Кодекс Pull Request

Каждый PR должен явно отвечать на три вопроса:
1. Какой новый закон мира появился? (не "добавил механику", а "теперь тепло распространяется")
2. Какие события этот закон слушает?
3. Какие события он создаёт?

Если ответа нет — PR отклоняется.

## 5. Расширенная архитектура (v2, согласована, ещё не реализована)

### 5.1 Consequences — последствия как долгоживущие данные

**Решение:** Consequences не являются отдельной подсистемой и не имеют собственного Scheduler. Они — часть World Projection, восстанавливаемой из Event Log.

```
Event Log → World Projection
  ├── Entities
  ├── Relations
  ├── Observations
  ├── Consequences
  └── Time
```

Каждый `TickPassed` — обычное событие. Правила читают текущее состояние Consequences в момент реакции на событие:

```
TickPassed → revengeRule → if hatred > 80 → RaidStarted
```

Отдельного `ConsequenceScheduler` не существует.

**Открытый вопрос (не решён, требует решения до реализации):** как истёкшие Consequences (`expiresAt` в прошлом) удаляются из Projection? Поскольку выделенного scheduler'а нет, предлагаемый механизм: правило `consequences.expire`, слушающее `TickPassed`, сравнивает `expiresAt` с текущим временем мира и эмитит `ConsequenceExpired`, который Projector использует для удаления записи. Это нужно зафиксировать в AGENTS.md явно, иначе Codex либо будет мутировать Projection в обход событий, либо не реализует очистку вовсе.

### 5.2 Прогресс — активация, а не генерация правил

**Решение для v1:** мир НЕ создаёт новые правила во время игры. Генерация исполняемого кода в рантайме — запрещена (это открыло бы риск выполнения непроверенного/LLM-сгенерированного кода).

Все правила:
- написаны заранее;
- зарегистрированы при запуске;
- могут быть только **активированы или деактивированы**.

Игрок открывает не новое правило, а уже существующее. Пример:

```
physics.wall_break — существует всегда,
но применяется только после PrincipleUnlocked("WeakPoint")
→ Rule Engine проверяет player.hasPrinciple("WeakPoint")
```

Никакой LLM не пишет код. Никакой runtime-компиляции. Никакой песочницы.

**Примечание:** это сознательный откат от более ранней идеи "мир создаёт новые правила в ответ на поведение игрока" в смысле генерации кода. Эта идея не отменяется полностью, а переносится в v3+ как отдельное исследовательское направление, требующее отдельной проработки безопасности (валидация, песочница).

**Уточнение (Emergence, снимает кажущееся противоречие с §7.3):** пример "склады стали каменными после серии поджогов" — это НЕ новое правило и не новый объект архитектуры. Это заранее написанное правило (например `warehouse.reinforce`), которое реагирует на накопленный Observation/Consequence (`arson_attempts_nearby > N`) и переключает атрибут уже существующей сущности (`Warehouse.material: "wood" → "stone"`), эмитя `WarehouseReinforced`. Мир не пишет код и не создаёт Rule — он лишь пересекает заранее заданный порог в уже зарегистрированном правиле. Формулировка "мир создаёт новый объект" из более ранних заметок неточна и заменяется этим определением, чтобы Codex не интерпретировал Emergence как разрешение на кодогенерацию.

### 5.3 Observations — наблюдения вместо ярлыков характера

**Решение:** характер игрока не хранится как ярлык (`Trait: Brave`), а как накапливаемые числовые наблюдения в Projection:

```
World Projection → Player → components → observations
  risk_taken: 27
  mercy: 11
  heat.near_fire: 8
```

Наблюдения — это проекции, пересчитываемые из событий:

```
MovementSucceeded → ObservationUpdated → Projection.observations.risk_taken++
```

Интерпретацию значений ("ты заметно склонен к риску") делает Narrative/LLM-слой, а не World. Отдельного `PlayerProfileManager` не существует.

### 5.4 Situations — долгоживущие правила во времени

**Решение:** Situation — не объект, не менеджер, не сценарий. Это обычное Rule, которое активируется/деактивируется событиями и действует на `TickPassed`.

Пример:

```
ForestFireStarted → активирует forest_fire.spread
forest_fire.spread слушает TickPassed → TreeBurned, SmokeSpread,
  AnimalsFled, VillageThreatened
RainStarted → forest_fire.spread.condition == false → правило ничего не делает
```

**Открытый вопрос (не решён, требует решения до реализации Situations):** где хранится состояние активности Situation и кто его проверяет?

Поскольку Rule обязано оставаться чистой функцией `(Event, ReadonlyWorld) → Event[]`, состояние активности не может быть флагом на самом правиле вне World. Рассматриваются два варианта:

- **(а) рекомендуемый:** активные Situations — часть World Projection (`world.activeSituations: Set<string>`). Правило `forest_fire.spread` при получении `TickPassed` само проверяет `world.activeSituations.has("forest_fire")` и возвращает `[]`, если условие не выполнено. Вся логика остаётся внутри Rule — не нарушает границу "infra ≠ gameplay".
- **(б) альтернативный:** RuleEngine фильтрует, какие правила вообще получают событие, на основе реестра активных Situations. Это превращает RuleEngine в место принятия игровых решений — потенциальное нарушение границы infra/gameplay.

Решение по (а) vs (б) должно быть зафиксировано в AGENTS.md одной строкой до того, как Codex начнёт реализовывать первую Situation.

### 5.5 Экономика — не Engine, а набор правил

Экономика не реализуется как отдельная подсистема (`EconomyEngine`). Она возникает как множество маленьких правил:

```
FoodScarcity → BreadPriceIncreased
IronDemandHigh → OrePriceRaised
BridgeDestroyed → WoodDemandUp
```

### 5.6 Магия → World Law

Понятие "магия" исключается из архитектуры полностью. Вместо `Intent → Magic Rule` используется `Intent → World Law`. Пример: закон `heat` применим и к костру, и к солнцу, и к лаве, и к собственному телу — это один и тот же закон, а не набор заклинаний.

### 5.7 Мир без игрока — Situations как процессы, а не NPC-симуляция

Не нужно симулировать каждого NPC отдельно. Нужно симулировать активные процессы (Situations, см. §5.4):

```
Tick → HarvestGrowing → BanditsNeedFood → RaidStarted
  → VillageFearRaised → PricesChanged
```

Живут процессы, а не каждый житель мира — это лучше масштабируется.

### 5.8 Персонаж без игрока — Player Strategy (декларативная политика)

Отказ от идеи автономного ИИ-агента для персонажа игрока. Вместо фиксированного сценария — декларативная политика: конечный набор пар "условие → действие", заранее одобренных игроком, оцениваемых обычным Rule на `TickPassed` при `PlayerOffline`:

```
PlayerOffline + player.strategy содержит:
  IF danger_nearby THEN return_home
  IF rumor_heard THEN record_rumor
  IF gold < threshold THEN work_as_blacksmith
  IF is_night THEN stay_indoors
```

Оба конца правила — и условие (`danger_nearby`, `is_night`, `gold < threshold`), и действие (`return_home`, `work_as_blacksmith`) — берутся из **заранее зарегистрированного конечного набора** предикатов и действий, а не формулируются свободно. Условие оценивается детерминированным Rule на основе World Projection (Observations, Relations, Consequences), а не LLM-суждением в моменте.

**Жёсткое ограничение (не подлежит расширению без пересмотра конституции):** оценка условий политики не делегируется LLM. Если "опасно ли сейчас" или "стоит ли работать кузнецом" решает LLM на лету, а не заранее заданный предикат над Projection — это прямое нарушение запрета `NPC.decide()` (§3), применённого к персонажу игрока. LLM может только описывать результат (Narrative), но не выбирать действие.

### 5.9 Биография — граф причинности, а не журнал

Биография персонажа не хранится как отдельная система записей. Она строится из Event Graph через identity-поля события (см. §9.9):

```
correlationId — связывает события одной "истории"/сессии
causationId   — ссылается на eventId события-причины (заменяет более раннюю идею causedEvents[])
```

Граф восстанавливается запросом (`SELECT * WHERE causationId = X`), а не хранением ссылок на потомков — это сохраняет append-only (см. §2.1): при появлении нового события D, вызванного A, мы пишем только D с `causationId = A.eventId`, не трогая уже записанное A.

Пример графа:

```
SavedVillage → MayorTrust+20 → GuildInvitation
  → BanditHatred → AssassinationAttempt
```

Считается одной из ключевых отличительных black-box фич проекта (наряду с Consequences и адаптацией мира — см. §7).

### 5.10 Временная шкала — представление, не данные

Timeline не хранится отдельно. Строится запросом к Event Log по диапазону времени и представляется Narrative/LLM-слоем в читаемом виде. Данные не дублируются.

### 5.11 Социальный граф — Relation Edges

Не `RelationshipManager`, а рёбра между сущностями со значениями, изменяемыми событиями:

```
Player → Guild: trust 40, respect 10, fear 0
HelpGuild → Trust +5
StealGuild → Trust -20
```

---

### 5.12 Ограничение действий по времени (Time & Action Budget)

Не отдельная подсистема — обычное правило `simulation.duration_check` в фазе Validation, реагирующее на Domain Event `<Action>Requested` (см. §4, §9.9 — например `MoveRequested`). Каждое действие имеет неявную длительность; правило сравнивает её с доступным временным окном (например, "успел бы игрок и прыгнуть, и ударить, и открыть дверь за один момент") и либо пропускает обработку дальше по фазам, либо эмитит `ActionRejected(reason: "insufficient_time")`. Данные о прошедшем/доступном времени — часть World Projection (Time, см. §5.1), отдельного таймера нет.

### 5.13 Контекст персонажа для Narrative (вместо отдельного "Character Engine")

Идея "персонаж — это развивающаяся личность, а не просто набор чисел" реализуется не как новое хранилище состояния, а как расширенный запрос Narrative Adapter к уже существующим проекциям: Observations (§5.3) + Relation Edges (§5.11) + активные Consequences (§5.1) + Biography-граф (§5.9). Narrative Adapter собирает эти данные в контекст для LLM при генерации описания или диалога. Никакая новая сущность в World не появляется — иначе Narrative стал бы источником фактов, что запрещено Authority Hierarchy (§6).

---

## 6. Authority Hierarchy (формализовано)

```
Event Log        — единственный источник истины
      ↓
World Projection — полностью вычисляется из Event Log
      ↓
Rules             — никогда не мутируют World напрямую, только создают Events
      ↓
Narrative / LLM   — интерпретирует происходящее, никогда не меняет состояние мира
```

Правила иерархии:
1. Event Log — единственный источник истины.
2. World Projection — полностью вычисляется из Event Log.
3. Rules никогда не изменяют World напрямую, а только создают новые события.
4. Narrative никогда не изменяет мир. Только интерпретирует события для игрока.
5. LLM не является источником истины. Он объясняет происходящее, но не определяет состояние мира.

## 7. Ключевые отличительные идеи проекта

Из всех обсуждённых идей три признаны наиболее ценными для уникальности проекта:

1. **Consequences как долгоживущие объекты**, которые спустя часы или игровые месяцы порождают новые события (§5.1).
2. **Биография как граф причинно-следственных связей**, а не список записей в журнале (§5.9).
3. **Мир, адаптирующийся к поведению игроков** — в v1 через активацию заранее написанных правил (§5.2), с генерацией новых правил как исследовательским направлением v3+.

## 8. MVP-0 / Iteration 0 (первая вертикальная реализация)

**Цель:** не сделать игру, не сделать магию, не сделать NPC — сделать полный рабочий цикл событий.

Реализуются только:
- `EventBus`: `append()`, `publish()`, `subscribe()`, `query()`.
- `IntentParser`: только `move north/south/east/west`, без NLP. Производит `PlayerCommand` (`MoveCommand`), не Event.
- **Command Handler** (минимальный, в составе `cli/` или `rule-engine/` для MVP-0): структурная проверка `MoveCommand` (известно ли направление) → эмитит `MoveRequested` (первый Domain Event, попадает в Event Log).
- `RuleEngine`: очередь событий без рекурсии (`dequeue → find rules → execute → enqueue → repeat`).
- `World Projection`: только позиция игрока и стены.
- Правило `physics.wall_block`: реагирует на `MoveRequested` → если стена, эмитит `MovementBlocked`, иначе `MovementSucceeded`. `MoveCommand` в Event Log не попадает — только `MoveRequested` и результат.
- `CLI`: простой REPL, выводящий события и текущую позицию игрока.
- Тесты: publish/subscribe, intent parser, command handler (structural validation), wall blocks/succeeds, projection обновление, очередь событий до опустошения.

**Явно не реализуется на этом шаге:** магия, NPC, discovery, Consequences, Situations, Observations, Biography, Economy, LLM-интеграция.

## 9. Детерминированность, время, ошибки, идемпотентность

Четыре принципа, добавленные после архитекторского ревью — без них Event Sourcing со временем ломается незаметно.

### 9.1 Детерминированность Rules (критично)

**Принцип:** один и тот же Event Log обязан восстанавливать абсолютно одинаковое состояние мира независимо от платформы, времени и количества запусков.

Rule обязано быть полностью детерминированным. Внутри Rule запрещено использовать:
- `Date.now()` / любые системные часы;
- `Math.random()` / любой источник случайности без явного seed из Event;
- генерацию UUID на лету;
- сетевые запросы, внешние API;
- прямой вызов LLM;
- любое глобальное изменяемое состояние вне переданного `ReadonlyWorld`.

Все источники неопределённости должны сначала стать Event. Например, случайное число не генерируется внутри Rule — Rule эмитит `RandomNumberRequested` как часть своего обычного возвращаемого `Event[]`, инфраструктура (не Rule, подписчик через EventBus — не Command Handler и не RuleEngine) генерирует значение один раз и добавляет `RandomNumberGenerated(value)` в Event Log; при replay используется записанное значение, а не генерируется заново. **Важно:** это Event → Event цепочка, без участия Command — контракт Rule `(Event, ReadonlyWorld) → Event[]` не нарушается ни на одном шаге (см. §9.9 про отдельную границу Command/Event).

**Принцип воспроизводимости:** любая ошибка должна воспроизводиться простым повторным проигрыванием Event Log — если баг не воспроизводится через replay, это признак нарушения детерминированности где-то в Rules.

### 9.2 Время — тоже Event

Внутренних часов не существует. Время в World Projection обновляется только через явные события:

```
TimeAdvanced / TickPassed / DayEnded / SeasonChanged
```

**Определение Tick — Tick Policy: TBD.** Это сознательно не решено сейчас, а не забыто (см. §11, Исследовательские вопросы). Зафиксировано: Tick — игровая, а не астрономическая единица (не секунда реального времени), продвигается явно через CLI/инфраструктурный Clock, добавляющий `TickPassed` с дельтой игрового времени в payload. Rules никогда не читают реальное время — только `world.time`. Точная гранулярность (ход/минута/час) и вопрос "сколько Tick проходит за одно действие игрока" должны быть решены до реализации первой Tick-based Situation, не раньше.

### 9.3 Domain Event vs Infrastructure Event

Соглашение об именовании и категоризации событий, чтобы не смешивать игровую семантику с техническими деталями:

- **Domain Events** — несут игровой смысл, свершившиеся факты мира: `MoveRequested`, `MovementSucceeded`, `MovementBlocked`, `ActionRejected`, `CommandRejected`, `WarehouseReinforced`, а также `TickPassed` и `RandomNumberGenerated`. Критерий отнесения к Domain: событие обрабатывается RuleEngine (влияет на дальнейшие Rules) и/или влияет на Projection — значит, оно часть факта мира, даже если инициировано инфраструктурой. `TickPassed` — прохождение игрового времени напрямую двигает пожары, экономику, урожай, Consequences; `RandomNumberGenerated` — Rules продолжают обработку на основе этого значения (см. §9.1), то есть оно тоже становится частью того, что произошло (например, "выпало критическое попадание со значением X").
- **Infrastructure/Operational Events** — чисто технические, никогда не обрабатываются RuleEngine, никогда не влияют на Projection: `ProjectionRebuilt`, `SnapshotCreated`, `RuleRegistered`. Эти события **не пишутся в канонический Event Log**, а пишутся в отдельный **Operational Log** — неавторитетный технический журнал для отладки и аудита инфраструктуры.

**Почему не два полноценных Event Log (снят вариант "разделить логи полностью"):** если бы `RandomNumberGenerated` ушёл в отдельный лог, RuleEngine пришлось бы читать из двух источников и мержить их для восстановления детерминированного порядка обработки — это воссоздаёт ровно ту проблему "двух источников истины", которую мы и пытаемся избежать. Поэтому граница проводится не по "кто породил событие" (Rule vs инфраструктура), а по "участвует ли событие в обработке Rules / Projection". Единственный канонический Event Log, из которого реплеится Projection, содержит только Domain Events — Operational Log существует отдельно и параллельно, никогда не участвует в replay мира.

Обе категории Domain Events (namespace-split, например `domain.TickPassed`) пишутся в один канонический Event Log (единый источник истины не нарушается), но разделяются на уровне неймспейса/префикса, чтобы при росте числа событий (десятки → сотни) можно было фильтровать и находить нужные без путаницы.

### 9.4 Политика обработки ошибок

Разграничиваются два разных случая:

- **Легитимный игровой отказ** — например, `MovementBlocked` (домен-специфичный отказ фазы Physics) или `ActionRejected(reason: "insufficient_time")` (общий отказ фазы Validation), либо `CommandRejected` на уровне Command Handler (структурная ошибка команды, см. §9.9). Всё это обычные Events, часть нормального потока, коммитятся в Event Log как любое другое событие.
- **Инженерная ошибка** — Rule бросило исключение (нарушение контракта, баг). Это НЕ Event. RuleEngine перехватывает исключение, останавливает обработку очереди для текущего top-level Command, **не коммитит** ни одно из уже сгенерированных в рамках этой обработки событий (атомарность на уровне одной команды), и возвращает вызывающей стороне (CLI/API) отдельную техническую ошибку, отличимую от `ActionRejected`/`MovementBlocked`.

### 9.5 Идемпотентность

Replay Event Log идемпотентен по построению — при детерминированных Rules (см. §9.1) одинаковый лог всегда даёт одинаковую Projection, повторных применений одного и того же Event в рамках нормального потока не происходит.

Проблема идемпотентности актуальна на **входе**, а не при replay: если внешний клиент (сеть, повторный клик, retry) дважды отправит один и тот же `PlayerCommand`, RuleEngine не должен дважды обработать его и породить дублирующиеся Domain Events. Решение: каждая внешняя команда несёт клиентский `idempotencyKey`; входная граница (CLI/API) проверяет наличие ключа перед обработкой и игнорирует дубликат.

### 9.6 Projection Purity Rule (инвариант конституции)

> Любая Projection полностью вычисляется из Event Log и не может хранить информацию, отсутствующую в нём. Кеши допустимы только как оптимизация чтения и должны быть полностью восстанавливаемы после удаления.

Ключевой тест: если удаление кеша меняет поведение системы — это уже не кеш, а скрытый второй источник истины, что запрещено. Это защищает от постепенного дрейфа, когда в Projection начинают добавлять "удобные служебные поля" в обход Event Log.

**Формальный тест корректности (обязателен для CI):** удалить Projection полностью → выполнить replay всего Event Log с нуля → полученная Projection должна быть идентична удалённой. Если тест не проходит — где-то в Projection есть данные, не выводимые из Event Log, и это нарушение инварианта, а не баг производительности.

### 9.7 Event Schema Evolution

Полноценная система миграций/апкастеров не строится сейчас — это было бы проектированием под гипотетическую проблему при нуле реально эволюционировавших событий. Но принцип фиксируется заранее:

> Новые поля в Event добавляются только как обратно совместимые (optional или с deterministic default при replay старых событий). Несовместимые изменения (переименование/удаление поля) требуют явного upcaster'а, реализуемого только при возникновении реальной необходимости — не заранее.

### 9.8 Event Identity

Каждое записанное в Event Log событие несёт формальный envelope:

```
Event {
  eventId       — уникальный идентификатор самого события
  type
  schemaVersion — версия формата payload для данного type (см. §9.7, Event Schema Evolution)
  payload
  timestamp     — игровое время (world.time), не системные часы (см. §9.1)
  correlationId — связывает события одной "истории"/цепочки обработки
  causationId   — eventId события-причины (см. §5.9, заменяет causedEvents[])
}
```

`schemaVersion` добавляется заранее не для немедленного использования, а чтобы через годы не пришлось задним числом менять сам envelope (что нарушило бы append-only, §2.1) — апкастеры (§9.7) будут явно знать, с какой версии payload переводить.

Это пригодится для Biography (§5.9), replay/debugging, трассировки и визуализации графа причинности — без этого причинно-следственный граф нечем было бы заполнять.

### 9.9 Command ≠ Event, и RuleEngine работает только с Events

Domain Event описывает факт, который уже произошёл в мире — не попытку его изменить. Rule при этом обязано сохранять контракт `(Event, ReadonlyWorld) → Event[]` без исключений — значит, `PlayerCommand` не может напрямую поступать в RuleEngine или на вход Rule. Отсюда — три уровня:

1. **PlayerCommand** (например `MoveCommand`) — существует только во время обработки запроса, в Event Log не пишется. Транспортная/интерфейсная сущность, а не факт мира.
2. **Command Handler** (infra, НЕ Rule, см. §2.3) — получает `PlayerCommand`, делает только структурную валидацию (известен ли тип команды, есть ли обязательные поля) без доступа к `ReadonlyWorld` и без игровой логики. Результат:
   - если команда структурно некорректна — эмитит `CommandRejected(reason)`;
   - если корректна — эмитит первый **Domain Event** вида `<Action>Requested` (например `MoveRequested`), который и попадает в Event Log.
3. **RuleEngine** — с этого момента видит только Domain/Infrastructure Events, никогда не видит `PlayerCommand`. Rules, реагируя на `MoveRequested` по фазам (Validation → Physics → Consequence → Notification), либо отклоняют действие игровыми событиями (`ActionRejected` — общий отказ, например по времени; `MovementBlocked` — домен-специфичный отказ физики), либо доводят обработку до Domain Event успеха (`MovementSucceeded`).

Отклонение — тоже факт, известный миру: после обработки `ActionRejected`/`MovementBlocked` мир действительно узнал новый факт ("попытка не удалась"), и это может повлиять на Observations/Consequences/Biography (например `ActionRejected(reason: "insufficient_time") → ObservationUpdated(impatience += 1)`). Ключевое отличие от прежней схемы: ни сама команда (`MoveCommand`), ни служебная структурная проверка не проходят через Rule — только через Command Handler, который стоит строго до границы Event Log.

### 9.10 Rule Phases — уточнение независимости

Фаза (см. §10, вопрос 3) определяет только порядок обработки: `Validation → Physics → Consequence → Notification`. Она не даёт Rule'ам права знать о существовании других правил в той же фазе или полагаться на порядок их выполнения внутри фазы. Каждое правило в фазе обрабатывает событие независимо, как если бы оно было единственным — это исключает скрытые зависимости между правилами одной фазы.

## 11. Исследовательские вопросы (сознательно отложено)

Это не пробелы и не забытые задачи — это темы, по которым решение осознанно не принимается сейчас, потому что любое решение сегодня было бы гаданием без реального опыта разработки. Явная фиксация здесь защищает от двух крайностей: (а) кто-то реализует это "по-своему" без обсуждения, (б) появляется ощущение незавершённости архитектуры.

- **Tick granularity** — точная единица игрового времени (ход/минута/час) и правило "сколько Tick проходит за одно действие игрока". Решается до реализации первой Tick-based Situation (см. §9.2).
- **Biography pruning policy** — граф `causationId`-связей (§9.8, §5.9) при миллионах событий: хранить полностью или только "значимые" события, и кто определяет значимость (обязательно детерминированный Rule, не LLM). Решается по факту, когда Biography реально начнёт реализовываться.
- **Runtime Rule Synthesis (v3+)** — генерация новых правил миром в ответ на накопленное поведение игрока, требует отдельной проработки безопасности (валидация, песочница). Явно запрещено в v1 (см. §5.2).
- **Distributed / Parallel RuleEngine** — сейчас RuleEngine последователен и однопоточен, вопрос параллельной обработки не имеет предмета, пока не появится реальная потребность в масштабировании.
- **Aggregate boundaries** (Player/Village/Guild/Kingdom как границы согласованности) — актуально только при появлении распределённой обработки или шардинга Projection; сейчас всё выражается через Entity без разделения на агрегаты.

## 12. Execution Model

§1–11 отвечают на вопрос "что существует в мире и кто обладает полномочиями". Этот раздел отвечает на вопрос "как именно исполняется мир" — формализует то, что раньше подразумевалось, но не было явно зафиксировано.

### 12.1 Snapshot-консистентность на уровне одного Event

Во время обработки одного извлечённого из очереди Event все подходящие Rules (по всем фазам, см. §9.10) читают **один и тот же снимок Projection**, сделанный в момент извлечения этого Event из очереди. Их результаты (`Event[]`) собираются вместе; Projection обновляется один раз — только после того, как все правила для этого конкретного Event завершили обработку, и только тогда начинается обработка следующего Event из очереди.

Это устраняет целый класс скрытых ошибок: зависимость результата от порядка регистрации правил, "грязное чтение" изменений, сделанных другим Rule в рамках той же итерации, и разное поведение при добавлении нового Rule в ту же фазу. По сути — аналог MVCC: все правила видят одну согласованную версию мира.

**Следствие:** Rule не имеет права предполагать что-либо о том, какие Events были обработаны раньше него в очереди, кроме того, что уже отражено в переданном ему snapshot Projection. Конструкции вида "если предыдущим обработанным событием было X" — запрещены: это скрытое состояние вне контракта `(Event, ReadonlyWorld) → Event[]`. Единственный легитимный способ Rule "узнать про прошлое" — прочитать его отражение в World Projection (например, в Observations или Consequences), а не полагаться на порядок очереди напрямую.

### 12.2 Транзакция top-level Command

Во время обработки top-level Command существует только временная (staged) Projection **и staged Event Log**. Generated Events, порождаемые Rules в процессе обработки очереди, накапливаются в in-memory staged Event Log — они становятся частью канонического Event Log только после успешного завершения всей транзакции целиком. До этого момента их не существуют ни в каком durable-хранилище: если бы Rule успел записать Event в канонический Log, а затем следующий Rule в той же цепочке бросил исключение, встал бы вопрос "как удалить уже записанное" — что нарушило бы append-only (§2.1). Именно поэтому запись в канонический Event Log происходит одним атомарным батчем, а не по одному событию за раз в процессе обработки.

Canonical (единственная авторитетная) Projection обновляется один раз — атомарно, вместе с коммитом staged Event Log — после успешного завершения всей обработки очереди, порождённой этой командой. Если где-либо в цепочке Rule бросает исключение (см. §9.4), откатывается вся цепочка целиком: staged Event Log отбрасывается, canonical Projection не изменяется вовсе, как если бы команда не поступала.

**Уточнение по итогам реализации MVP-0 (Iteration 0):** механизм обновления Projection — прямой синхронный вызов `WorldProjector` со стороны `RuleEngine` как часть атомарного коммита батча, а не подписка через generic `EventBus.subscribe()`. Причина: pub/sub с произвольными подписчиками не гарантирует, что Projection обновится синхронно и ровно один раз сразу после коммита canonical Event Log — а именно эта гарантия и есть содержание §12.1–12.2. `EventBus.subscribe()` остаётся корректным каналом для неавторитетных read-only-потребителей (Narrative Adapter, CLI-printer, отладочные логи), которым синхронность с коммитом не требуется; для них вводится `subscribeAll()` (wildcard-подписка). `WorldProjector` в эту категорию не входит и не должен туда переводиться.

### 12.3 Политика конфликтов

Если два правила одной фазы производят взаимоисключающие авторитетные Domain Events для одного `<Action>Requested` (например, одно эмитит `MovementSucceeded`, другое — `MovementBlocked`) — это **не игровая ситуация, а архитектурная ошибка Rule Set**, и должна выявляться тестами, а не разрешаться рантайм-механизмом приоритетов. Для одного `<Action>Requested` только одно правило в данной фазе имеет право быть "владельцем" авторитетного исхода; остальные правила той же фазы могут реагировать побочно (Observations, логирование), но не могут производить конкурирующий исход.

### 12.4 Read Models

World Projection может состоять из нескольких специализированных Read Models (`Player`, `Economy`, `Village` и др.), однако каждая из них полностью вычисляется из Event Log и не является самостоятельным источником истины — Projection Purity (§9.6) распространяется на каждый Read Model по отдельности. Это явно закрывает соблазн позже завести отдельную "экономическую БД" в обход Event Log.

### 12.5 Snapshot (кэш Projection)

Snapshot — это кэш Projection на определённый `eventNumber` (см. §12.7), а не источник истины. Свойства, следующие напрямую из Projection Purity (§9.6), а не являющиеся отдельной оптимизацией:

- Snapshot можно удалить в любой момент без потери информации.
- Snapshot полностью восстановим replay'ем Event Log с начала (или с предыдущего валидного Snapshot).
- Snapshot никогда не содержит данных, которых нет в Event Log.

Механизм снапшотирования не реализуется сейчас — это оптимизация под объём данных, которого пока не существует (см. §11, Исследовательские вопросы, где аналогичная логика применена к Biography pruning). Принцип фиксируется заранее, чтобы при реализации не изобрели снапшот, нарушающий Projection Purity.

### 12.6 Rule Registration — явный контракт

Формализация уже принятого в §5.2 запрета рантайм-регистрации правил:

```
RuleRegistry.register(rule: {
  id: string
  phase: "validation" | "physics" | "consequence" | "notification"
  listens: EventType[]
  produces: EventType[]
})
```

`produces` — декларативный список типов Domain Events, которые правило может эмитить. Не влияет на рантайм-поведение (RuleEngine не блокирует эмит событий вне списка на старте v1), но даёт автоматическую документацию, генерацию графа зависимостей Rules, и основу для статических проверок (например, обнаружение потенциальных конфликтов из §12.3 ещё до запуска тестов — если два правила одной фазы декларируют пересекающиеся `produces` с взаимоисключающей семантикой, это сигнал для ревью).

Все Rules регистрируются при старте приложения через `RuleRegistry`. Динамическая регистрация (добавление/удаление Rule во время работы) запрещена — это тот же инвариант, что и запрет runtime rule generation (§5.2), только на уровне механизма, а не только политики.

### 12.7 Версия мира

Projection несёт `eventNumber` (порядковый номер последнего применённого Event) наравне с `world.time` (§9.2). Это отдельная величина: `eventNumber` — техническая (сколько событий обработано), `world.time` — игровая (сколько игрового времени прошло). Помогает при отладке и обязательна для корректной работы Snapshot (§12.5) — снапшот всегда привязан к конкретному `eventNumber`.

### 12.8 Ограничение Parser

> Parser выполняет только синтаксическую и семантическую интерпретацию пользовательского ввода. Он никогда не принимает игровые решения и не разрешает неоднозначность, если для это требует знание мира. Любая неоднозначность должна быть разрешена либо пользователем (уточняющий вопрос на уровне интерфейса), либо Rules после появления Domain Event.

Это распространяется и на будущий NLP/LLM-парсер: даже когда `move north` превратится в свободный текст, Parser переводит текст в `PlayerCommand` и не более того. Если для интерпретации неоднозначной фразы требуется знание текущего состояния мира ("а что значит 'ударить' в данной ситуации") — это уже задача Rules, читающих World Projection, а не Parser'а. Иначе LLM в парсере постепенно начнёт "догадываться", что игрок хотел, и станет скрытым источником игровых решений в обход Rules — прямое нарушение Authority Hierarchy (§6).

### 12.9 Политика удаления событий

Дополнение к append-only (§2.1): исторические Events никогда не удаляются из Event Log. Архивирование (перенос старых событий в холодное хранилище) допускается только в связке Snapshot + архив Log, и только после того, как Snapshot на соответствующий `eventNumber` подтверждён как валидный (реплеится в идентичную Projection, см. §9.6). Архивный Log при этом не удаляется физически — становится источником истины на случай, если Snapshot когда-либо потребуется перепроверить или инвалидировать.
